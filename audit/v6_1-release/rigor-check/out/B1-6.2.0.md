**Rigor: sprint.** You're the only contributor, there's no production data, and the code is under git so it can be undone. That means no reviewer agents, no phase gates, no hooks, no Skills and no MCP servers. Nothing here has a failure those would prevent.

The one real risk in this project isn't the code. It's the agent running the tool on your actual photo folders. A bad rename of 4,000 family photos can't be undone with git, so most of the setup below exists to stop that.

## 0. Before the first session

```
git init && git add -A && git commit -m "baseline"
```

Git is how you undo the agent's code changes, so set it up first. Your working directory is currently empty and isn't a git repo, so run this in the real project folder.

## 1. `CLAUDE.md` (repo root)

```markdown
# photo-rename

Personal CLI: renames photo files using their EXIF capture date. Single user, Windows.

## Commands
- Tests: `python -m pytest -q`
- Run the CLI only against `tmp_path` fixtures or a scratch copy, never a real photo folder.

## Behavior contract (don't change without asking)
- **Dry run is the default.** Real renames need an explicit `--apply`.
- Date source: EXIF `DateTimeOriginal`, then `DateTimeDigitized`. Never use filesystem mtime unless `--fallback-mtime` is passed.
- Name format: `YYYY-MM-DD_HHMMSS<ext>` with the extension lowercased. On a collision add `_1`, `_2`, …
- **Never overwrite an existing file.** Never delete anything.
- Files with no usable date are skipped and listed in the summary. They aren't an error.

## Code
- `src/` layout. Pure functions (read date → build name → plan renames) are kept apart from the
  part that touches the filesystem (apply the plan). Test the pure parts directly.
- Test images are generated inside tests (Pillow + EXIF bytes). Don't commit binary fixtures.

## Working rules
- Routine, no need to ask: edit code and tests, run pytest, add and adjust tests, commit to the current branch.
- Stop and ask before: running the CLI with `--apply` on any path outside a pytest `tmp_path`,
  changing the behavior contract above, adding a runtime dependency beyond one EXIF library,
  or pushing / rewriting git history.
```

That's about 30 lines, and it should stay short. When the agent repeats the same mistake twice, add a rule here for it. Don't add rules ahead of time.

## 2. `.claude/settings.json`

```json
{
  "permissions": {
    "allow": [
      "Bash(python -m pytest:*)",
      "Bash(pytest:*)",
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Bash(git log:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(pip install -e:*)"
    ],
    "deny": [
      "Bash(git push:*)"
    ]
  }
}
```

Running the CLI itself is deliberately left off the allow list, so you get a prompt every time the agent tries it. That prompt is a mechanism backing the CLAUDE.md rule, so you're not relying on the rule text alone. I didn't add a hook because the prompt is enough for one person who watches the session.

On Windows, Claude Code may run commands through its PowerShell tool instead of Bash. If you keep getting prompts for pytest, run `/permissions` once and approve the exact form it shows. Don't guess the rule syntax.

## 3. First session prompt

```
Goal: a working core for photo renaming, test-first. Read CLAUDE.md and the existing
code/tests before writing anything.

Build:
1. `read_capture_date(path) -> datetime | None` (DateTimeOriginal → DateTimeDigitized → None).
   Choose one EXIF library (Pillow preferred if already present) and say why in the report.
2. `build_name(dt, ext) -> str` per the format in CLAUDE.md.
3. `plan_renames(paths) -> list[(src, dst)] + skipped list`. Handle collisions within the
   batch AND with files already on disk. No filesystem writes here.
4. `apply_plan(plan)`: refuses to overwrite and re-checks the destination right before each rename.
5. CLI: `photo-rename <dir> [--apply] [--recursive]`. Dry run prints the plan and a summary.

Tests (generate the images in tmp_path): no EXIF, only DateTimeDigitized, two photos with the same
second, destination already exists, uppercase .JPG, a file that is already correctly named
(no-op), and dry run leaving the directory byte-identical.

Done = `python -m pytest -q` passes, and a dry run on a tmp_path fixture dir shows the
expected plan.

Don't stop for test failures, refactors, or choosing between reasonable designs. Pick one
and note it. Stop only for the items under "Stop and ask" in CLAUDE.md.

Finish with a 5-line report: what was built, library choice, test count/result,
open decisions for me, and files changed. Then commit.
```

## When to add more

- **Add a PreToolUse hook that blocks `--apply` outside temp directories** if you start running long sessions without watching them. That's the point where a permission prompt stops being enough.
- **Move to standard rigor** if anyone else contributes or you publish it to PyPI.
- **Revisit HEIC/RAW support, video files and timezone handling** after the core works. Each one is a separate session with its own prompt.

I skipped a separate design brief and subagents on purpose. For a single-module CLI they'd be ceremony with no failure to prevent.
