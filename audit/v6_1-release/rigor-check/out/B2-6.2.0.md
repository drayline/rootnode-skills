## `CLAUDE.md`
```markdown
# recon — payments reconciliation service

Matches processor settlements and bank statements against our ledger and flags breaks for finance ops.
Production Postgres is the system of record. Money errors and broken migrations are the two expensive failures here.

## Commands
- `make test`: unit and integration tests. Needs local Postgres: `docker compose up -d db`
- `make lint`: also run `squawk <file>` on any new migration
- `make db-migrate-local` / `make db-rollback-local`: local database only
- Golden reconciliation fixtures: `tests/fixtures/settlements/`. Regenerate only when asked.

## Money rules (non-negotiable)
- Store amounts as integer minor units (`bigint`) with an ISO-4217 `currency` column. Never use float, in code or in SQL.
- Never compare amounts across currencies without an explicit FX record.
- Ledger and match-history tables are append-only. Corrections are new rows that reference the original.
- Every ingest and match write is idempotent on a natural key (processor + settlement id + line).
- Rounding happens only in `recon/money/`. Do not add another rounding site.

## Migrations
Detailed rules are in `.claude/rules/migrations.md`. In short:
- Merged migrations are immutable (a hook enforces this). Fix forward with a new file.
- Use expand/contract. A migration must work with both the previous and the next app release.
- Every new migration needs a working down-migration or an `-- irreversible: <reason>` header.
- Run the `migration-reviewer` subagent before you call a migration done. Paste its verdict into the PR description.
- Migrations that touch `ledger_*` or `match_*` tables need a human sign-off before you commit. Ask for it.

## Scope
**Routine: do these without asking.** Read the repo. Edit app code and tests. Create new migrations. Run make
targets, squawk and the local database. Create branches and commit on them. Push feature branches. Open draft PRs.

**Do, then tell me in your summary.** Dependency bumps, changes to `recon/money/`, changes to matching tolerance
or ordering, and changes to golden fixtures.

**Out of scope. Settings or hooks block these; do not work around them.** Production or staging databases and
credentials, deploying, merging, pushing to `main`, editing merged migrations, `.env*`, `.github/workflows/`, `deploy/`.

## Stop and ask
Stop only in these cases:
1. The next action cannot be undone. Examples: destructive SQL against anything other than local Docker Postgres, a force-push.
2. A decision could go either way and only an engineer can make it. Examples: what counts as a match, a tolerance value, retention, or whether a migration may be irreversible.
3. A hook blocks you. Report it. Do not rephrase the command to get past it.
4. A headless run reaches its budget or turn cap.

Do not stop for failing tests, lint errors or missing local dependencies. Fix them and carry on.

## Working style
- Before you change matching logic, add a golden-fixture test that shows the current behaviour.
- Keep PRs to one concern. Schema and code changes for a contract step ship in separate PRs.

## Session report
After a task that changed files, write `reports/session_{YYYYMMDD-HHMM}Z.md`. Include the branch, HEAD SHA,
`git diff --name-status` against the base, the test, lint and squawk exit codes, the reviewer verdict, and a
"not verified" list. Commit it with the next commit, not on its own.
```

## `.claude/rules/migrations.md`
```markdown
---
paths:
  - "db/migrations/**"
---
# Migration rules (zero-downtime weekly deploys)
Migrations run before the app rolls out, so the OLD app briefly runs against the NEW schema. Every migration must survive that.

## Expand / contract
- Expand (release N): add nullable columns, tables and indexes. The app writes to both old and new.
- Backfill: a separate, batched, resumable job in `recon/jobs/backfill_*`, never inside the migration.
- Contract (release N+1 or later): drop old columns only after no running release reads them. Never rename in place.

## Lock safety
- Build and drop indexes with `CONCURRENTLY`, in a migration with no transaction wrapper.
- For NOT NULL: add the column nullable, backfill, then `CHECK (col IS NOT NULL) NOT VALID`, then `VALIDATE`.
- Add foreign keys `NOT VALID` and validate them in a later migration.
- Start every migration with `SET lock_timeout = '3s'` and a `statement_timeout`.
- No `ALTER COLUMN TYPE` on `ledger_*`, `match_*` or `settlement_lines`.

## Done means
1. `squawk` is clean, or each warning is justified in a SQL comment.
2. `make db-migrate-local && make db-rollback-local && make db-migrate-local` succeeds.
3. `make test` passes.
4. `migration-reviewer` returns PASS or PASS-WITH-NOTES, pasted into the PR.
```

## `.claude/agents/migration-reviewer.md`
```markdown
---
name: migration-reviewer
description: Reviews one new Postgres migration for deploy-overlap safety, lock safety, reversibility and money rules. Use for every new file in db/migrations/ before opening a PR.
tools: Read, Grep, Glob, Bash
model: opus
---
Your job is to find what breaks in this migration, not to approve it. You get one migration path and the PR's intent in at most 5 lines.
1. Deploy overlap: does the code on `origin/main` (`git show origin/main:<path>`) still work against the new schema?
2. Locks: look for ACCESS EXCLUSIVE locks on large tables, non-concurrent indexes, a missing lock_timeout, FKs or CHECKs without NOT VALID, or a backfill inside the migration.
3. Reversibility: does the down-migration really restore the old schema? If it's marked irreversible, is the reason real?
4. Money: look for float types, amounts without a currency, or UPDATE/DELETE on append-only tables.
5. Run `squawk` and fold in what it reports.
Only read files and run git and squawk. Do not edit anything.
Return at most 25 lines: `VERDICT: PASS | PASS-WITH-NOTES | FAIL`, then findings as `[severity] file:line — what breaks, under what condition`, then `NOT CHECKED: ...`. No file contents, no style comments.
```

## `.claude/hooks/guard-merged-migrations.sh`
```bash
#!/usr/bin/env bash
# Blocks edits to any migration already on origin/main. New files are allowed. Exit 2 = block.
set -euo pipefail
file="$(jq -r '.tool_input.file_path // empty')"; [ -z "$file" ] && exit 0
root="${CLAUDE_PROJECT_DIR:-$(git rev-parse --show-toplevel)}"
rel="${file//\\//}"; root_fwd="${root//\\//}"; rel="${rel#"$root_fwd"/}"
case "$rel" in db/migrations/*) ;; *) exit 0 ;; esac
if ! git -C "$root" rev-parse --verify -q origin/main >/dev/null; then
  echo "BLOCKED: cannot resolve origin/main; run 'git fetch origin'." >&2; exit 2; fi   # fail closed
if git -C "$root" cat-file -e "origin/main:$rel" 2>/dev/null; then
  echo "BLOCKED: $rel is merged to main and immutable. Write a new forward migration." >&2; exit 2; fi
exit 0
```

## `.claude/hooks/guard-prod.sh`
```bash
#!/usr/bin/env bash
# Backup check only. The real control is that no prod credentials exist on dev machines.
set -euo pipefail
cmd="$(jq -r '.tool_input.command // empty')"; [ -z "$cmd" ] && exit 0
# Replace with your real hostnames, kube contexts and secret variable names:
prod='(prod|production|staging)[-_.]?(db|pg|postgres|rds)|recon-prod|PROD_DATABASE_URL|--env[= ]+(prod|production|staging)'
if grep -Eiq "$prod" <<<"$cmd"; then
  echo "BLOCKED: command references a production/staging target. Ask an engineer." >&2; exit 2; fi
if grep -Eiq '\b(drop (table|schema|database)|truncate)\b' <<<"$cmd" && ! grep -Eq 'localhost|127\.0\.0\.1|docker compose exec db' <<<"$cmd"; then
  echo "BLOCKED: destructive SQL outside the local Docker database." >&2; exit 2; fi
exit 0
```
A hook blocks only when it exits with code 2; any other non-zero exit lets the action go ahead. Matching commands by pattern is a backup and can be got around, which is why the deny list and the missing credentials do the real work.

## Agent setup and weekly deploys
- **One agent per engineer, plus one reviewer.** The reviewer needs to come from a separate session so its opinion doesn't depend on the work it's checking. Nothing else here needs its own agent. Leave Ultracode off by default.
- **Weekly release prep** (optional, the only automated run): `claude -p "list migrations and money/ changes between the last release tag and main; flag any contract-step migration whose expand step hasn't shipped" --max-budget-usd 5 --max-turns 40`, read-only.
- **The deploy itself stays human and runs in CI.** Claude can draft release notes but never runs the deploy.
