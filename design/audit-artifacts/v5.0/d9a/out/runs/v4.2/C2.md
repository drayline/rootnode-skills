DESIGN mode: a session prompt for an unattended overnight run, with the controls it needs outside the prompt.

## Fix these before the first run

1. **The phase order may be backwards for your ORM.** Alembic autogenerate, Django `makemigrations` and Prisma all generate migrations *from* the models. Your order (migrations first, models last) only works if the migrations are written from a spec. If you run it with an autogenerating tool, phase 1 has nothing to work from, and phase 3 creates drift. The prompt handles this with a drift check as the final gate. But if your tool works from models, change the phase order before using this. `[generalizable]`
2. **I don't know your stack.** I don't know which ORM, migration tool or database engine you use, or how to connect to staging. Your global CLAUDE.md bans placeholders in commands, so all of these are in one Run configuration block. Pre-flight halts if any `{` is left in it. You fill the block once; nothing else in the prompt has blanks.
3. **"Staging only" written in the prompt is just a preference, not a control.** With nobody watching, a hook and permission denies have to back it up (see Enforcement below). `[cc-anti-patterns §4.4]`
4. **Do a short trial run first.** Before the first overnight run, run once with `RUN_MODE: phase1-only` in a session you're watching. This catches configuration mistakes while someone can still see them. `[generalizable — pump-primer pattern]`

## The session prompt

Save it as `prompts/migration_overnight.md` and launch it headless.

````markdown
# Autonomous run: three-phase database migration (UNATTENDED)

## Critical
- Nobody is watching. Never ask a question and never wait for input. Any ambiguity, unmet precondition or failed gate means HALT (see Halt protocol). Halting is a correct outcome. Guessing is not.
- Write only to: MIGRATIONS_DIR, MODELS_DIR, reports/migration_{RUN_ID}/, and git commits on branch migration/{RUN_ID}.
- The only database you may touch is the one in $STAGING_DATABASE_URL, plus $SCRATCH_DATABASE_URL if it is set. Never write a database URL, password or host credential into any file or report; write it as <redacted>.
- Do not push, merge, force, rebase, or commit to main. Do not modify CLAUDE.md or any settings file.
- Ultracode off. No dynamic workflows. At most one subagent at a time.

## Run configuration (operator fills before launch)
RUN_ID: {RUN_ID}
RUN_MODE: {full | phase1-only}
MIGRATION_SPEC: {MIGRATION_SPEC_PATH}
MIGRATION_TOOL: {TOOL_NAME_AND_VERSION}
MIGRATIONS_DIR: {MIGRATIONS_DIR}
MODELS_DIR: {MODELS_DIR}
GENERATE_CMD: {GENERATE_CMD}
RENDER_SQL_CMD: {OFFLINE_SQL_RENDER_CMD or "unsupported"}
APPLY_CMD: {APPLY_CMD}
DOWNGRADE_ONE_CMD: {DOWNGRADE_ONE_CMD}   # used ONLY against $SCRATCH_DATABASE_URL
CURRENT_REVISION_CMD: {CURRENT_REVISION_CMD}
DRIFT_CHECK_CMD: {DRIFT_CHECK_CMD}       # must exit 0 when the models match the schema
BACKUP_CMD: {BACKUP_CMD}
TEST_CMD: {TEST_CMD}
STAGING_HOST_ALLOWLIST: {STAGING_HOSTS}
PRODUCTION_HOST_DENYLIST: {PRODUCTION_HOSTS}
DESTRUCTIVE_OPS_AUTHORIZED: {none | explicit list of table.column operations}

## Mission
Done means all of these are true, each shown by command output saved to reports/migration_{RUN_ID}/:
(a) every change in MIGRATION_SPEC exists as exactly one migration operation, and no operation exists that the spec doesn't call for;
(b) staging is at the head revision of the new migrations;
(c) DRIFT_CHECK_CMD against staging exits 0;
(d) TEST_CMD has no failures that weren't already in the pre-flight baseline.
Check this final state at the end. Do not treat a step having run as proof that its result is correct.

## Reporting (append-only)
Directory: reports/migration_{RUN_ID}/
- STATUS.md: append one timestamped line after every step (phase, step, result, artifact path). Never edit or delete earlier lines.
- HEARTBEAT.md: overwrite with the current UTC time at the start of every step.
- Phase artifacts are named in each phase below. HALT.md is written only if you halt. RUN_SUMMARY.md is always written last.

## Pre-flight (all must pass, or HALT)
1. List the Skills available in this session and record them in STATUS.md. If rootnode-critic-gate is installed, record that too; it is optional for this run.
2. Read CLAUDE.md, MIGRATION_SPEC, and the last 10 commits (`git log --oneline -10`).
3. If the Run configuration still contains `{`, HALT.
4. `git status --porcelain` must print nothing. Create and switch to branch migration/{RUN_ID} from the current HEAD. HALT if the branch already exists.
5. Confirm every configured tool resolves: run each with `--version` or `--help`. HALT on any that fail to resolve.
6. $STAGING_DATABASE_URL must be set. Extract its host. The host must match STAGING_HOST_ALLOWLIST and must not match PRODUCTION_HOST_DENYLIST. Record only "host check: PASS" or "FAIL".
7. Run TEST_CMD and save the output to preflight_tests.txt as the baseline. If it does not run at all, HALT. Failing tests are allowed; list them in the baseline.
8. Run CURRENT_REVISION_CMD against staging and record the starting revision.

## Phase 1: generate migration files
1. Read MIGRATION_SPEC and write phase1_change_inventory.md: one row per intended change, with columns id | table | operation | class (additive / data-moving / destructive) | spec line ref. If the spec leaves an operation unclear, HALT.
2. If a destructive row is not listed in DESTRUCTIVE_OPS_AUTHORIZED, HALT before generating anything.
3. Generate migrations with GENERATE_CMD, writing only into MIGRATIONS_DIR. Every data-moving operation must have a working downgrade, not an empty stub.
4. If RENDER_SQL_CMD is supported, render the SQL to phase1_rendered.sql.
5. If $SCRATCH_DATABASE_URL is set, run apply, then DOWNGRADE_ONE_CMD once per new migration, then apply again, all against scratch only. Save the log to phase1_reversibility.txt. Any failure means HALT.
6. Reconcile: count the inventory rows and count the generated operations. Write both counts, and the mapping between them, to phase1_reconciliation.md. A mismatch means HALT.
7. Spawn the Refuter (brief below). On ACCEPT, continue. On REWORK, fix the must-fix items and spawn a new Refuter. If there is no ACCEPT after 3 cycles, HALT.
8. Commit with message `migration {RUN_ID}: phase 1 generated migrations`. If RUN_MODE is phase1-only, go to Closeout.

### Refuter brief (fresh subagent, not a fork)
- Goal: decide whether the new files in MIGRATIONS_DIR implement MIGRATION_SPEC exactly.
- Scope: MIGRATION_SPEC, MIGRATIONS_DIR, phase1_change_inventory.md, phase1_rendered.sql.
- May change: nothing. Tools: Read, Grep, Glob, and Bash for read-only commands only. No database connections.
- Verify against the files: each spec change maps to one operation; there are no extra operations; downgrades exist; destructive operations are authorized; there are no hard-coded credentials.
- Do not: edit files, suggest changes outside the spec, or treat the builder's notes as evidence.
- Already known: tool = MIGRATION_TOOL. The inventory and reconciliation already exist.
- Return: line 1 is ACCEPT or REWORK, then must-fix items as `file:line - issue`. At most 300 words. Write any longer findings to phase1_refuter_notes.md and return only that path.

## Phase 2: apply to staging
1. Repeat pre-flight step 6 (host check) immediately before connecting.
2. Run BACKUP_CMD into reports/migration_{RUN_ID}/backup/ (git-ignored). Confirm the backup file exists and is non-empty, and record its size and sha256. If it is missing or empty, HALT.
3. Run APPLY_CMD against staging and save the full log to phase2_apply.log.
4. Run CURRENT_REVISION_CMD. It must equal the head revision of the phase-1 migrations; otherwise HALT.
5. Dump the post-apply schema (schema only) to phase2_schema_after.sql.
6. If apply fails or the revision does not match: HALT immediately. Do NOT run a downgrade on staging, run manual SQL, retry the apply, or restore the backup. Record the observed revision in HALT.md.

## Phase 3: update ORM models
1. Edit MODELS_DIR only, so the models match the schema now on staging. Do not change unrelated models.
2. Run DRIFT_CHECK_CMD against staging. It must exit 0. You get up to 3 fix cycles; after that, HALT.
3. Run TEST_CMD and save the output to phase3_tests.txt. Any failure that is not in preflight_tests.txt means HALT. Do not delete, skip or mark tests expected-to-fail.
4. Commit with message `migration {RUN_ID}: phase 3 ORM models`.

## Halt protocol
Write HALT.md containing: which trigger fired, the phase and step, the command and the last 40 lines of its output, the state of staging (its revision, or "untouched"), the last commit SHA, and the next action you recommend to the operator. Append "HALTED" to STATUS.md. Write RUN_SUMMARY.md, then stop. Do not try a workaround.
Halt triggers, in addition to those named in the steps above: any instruction you are not authorized for here; an ambiguous root cause; a change touching files outside the write list; any sign the target database is not staging; tests that start failing in code this run did not change.

## Closeout: RUN_SUMMARY.md (always written)
- Outcome: COMPLETE / HALTED at phase N step M / PHASE1-ONLY COMPLETE.
- End-state assertions (a) through (d) from the Mission. For each, give PASS / FAIL / NOT REACHED and the path to the artifact that proves it.
- Counts (operations generated, migrations applied, models changed, tests passed and failed), computed from the artifacts as you write them. Cross-check against the reconciliation and test files.
- Commits on the branch, staging revision before and after, and the backup sha256.
- Open questions for the operator.
Forbidden wording: "should work", "probably fine", "looks good". Every claim must cite an artifact.
````

## Enforcement outside the prompt

These four controls are the safeguards; the prompt explains the rules but doesn't enforce them.

- **PreToolUse hook on Bash.** Block any command whose text matches the hosts in `PRODUCTION_HOST_DENYLIST` or a production connection-string variable name. Also block `git push`, `--force` and `git checkout main`. Enforcement belongs in hooks, not the prompt. `[CC_EG §6]`
- **`.claude/settings.local.json`.** Add an allow-list for the configured migration, test and backup commands, plus a `permissions.deny` covering `Bash(git push:*)` and edits to `CLAUDE.md` and `.claude/**`. `[product fact 2026-09-09 — verify against the running Claude Code version]`
- **Refuter agent file.** Set `tools: Read, Grep, Glob, Bash`, `maxTurns: 25`, and a model at or above the orchestrator's tier. The reviewer must not be weaker than the builder. `[product fact 2026-09-09 — verify against the running Claude Code version]`
- **Hard time limit.** The agent can't keep a wall-clock limit itself. Schedule a Windows Task Scheduler kill (`Stop-Process -Name claude -Force`) for a fixed morning time.

## Where design stops and the overnight run starts

- **Ready to launch when:** the Run configuration is filled, the hook and denies are installed, and the `phase1-only` trial has finished with an ACCEPT from the Refuter.
- **Bring it back to a design session if:** HALT.md cites the same trigger on two runs, the drift check fails on a clean phase 3 (which points to the phase-order problem), or you want a second database target.
- **Not recommended:** critic-gate formalization, mode-router, or extra agents. One independent review of phase 1 plus external gates covers the risk here.

## Open questions

1. Which migration tool and ORM? This decides whether the phase order needs to flip.
2. Is a scratch database available? Without one, migrations are never tested for reversibility before they reach staging.
3. Should the git-ignored backup in `reports/` be kept or deleted after a successful run? It may contain staging data.
