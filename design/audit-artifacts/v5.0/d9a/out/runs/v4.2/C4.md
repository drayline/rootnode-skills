DESIGN MODE: a Builder-to-Refuter loop for a pnpm TypeScript monorepo that implements `specs/*.md`. This is a narrow ask, so I skipped the design-brief interview. The assumptions I made are listed at the end.

**Recommendation:** use the minimal loop of Orchestrator, Scout, Builder, Refuter and back to the Orchestrator. Add a Debugger only when the escalation rule below triggers. Don't use the four-agent verification topology. Ordinary spec implementation needs one independent re-check, not perspectives that are designed to conflict `[generalizable — cc-delegation-patterns §4]`.

---

## 1. Role table

Models are given as tier aliases (`haiku` / `sonnet` / `opus`) so the agent files stay valid when model versions change. Current mapping: Haiku 5.5, Sonnet 5.5, Opus 5.5. That mapping is a fact as of 2026-10-29 and should be refreshed, not assumed.

| Role | Work | Model | Effort | Tools | Isolation | maxTurns | Returns |
|---|---|---|---|---|---|---|---|
| Orchestrator (main thread) | Reads the spec, writes briefs, runs the loop, decides merges, escalates | opus | high | full | — | — | — |
| Scout (project `Explore` override) | Maps the packages, files, exports and tests the spec touches | haiku | low | Read, Grep, Glob | — | 15 | ≤25 lines: paths and line refs |
| Builder | Implements the spec, writes tests, runs the suite | sonnet by default; `opus` per invocation for hard specs | high | full minus `Agent` | `worktree` | 60 | ≤40 lines: report and deviation list |
| Refuter | Checks the Builder's diff against the spec independently and reruns the suite | opus | high | Read, Grep, Glob, Bash | fresh, not a fork | 30 | ≤30 lines: ACCEPT or REWORK with must-fixes |
| Debugger (escalation only) | Finds the root cause when two REWORK rounds fail the same criterion | opus | xhigh | full minus `Agent` | `worktree` | 40 | ≤35 lines: competing hypotheses, each with a predicted observation |

Rules behind the table:
- **The reviewer must be at least as capable as the Builder.** Save money on the Scout, never on the Refuter. A weaker reviewer just agrees with the Builder `[generalizable — CC_EG §3]`.
- **The Refuter has no Write or Edit tools,** so it can't quietly fix what it was asked to judge. Its Bash use is limited to `pnpm` and read-only `git` commands (rule L6) `[Anthropic docs — tools allowlist]`.
- **The Scout must be a project agent named `Explore`.** Since v2.1.198 the built-in Explore inherits the main model, so without an override, scouting is billed at Opus rates `[Anthropic docs]`.
- **Choose the Builder's tier when you spawn it, by rule.** Pass `model: opus` when the spec touches 3 or more packages, changes a public export, or is a rework after a Debugger round. Don't leave it to the Orchestrator to "notice" a hard spec `[generalizable]`.

## 2. Delegation briefs

Each brief has the eight required fields. `<...>` marks a value the Orchestrator fills in from the spec at spawn time. These are slots in a template, not commands to run.

### 2.1 Scout brief
| Field | Content |
|---|---|
| Goal | Find every file, export, call site and existing test that `specs/<spec>.md` will touch. |
| Scope | The workspace root `pnpm-workspace.yaml`, the `package.json` files, and the packages the spec names. |
| May change | Nothing. |
| Verify | Every path you return exists. Confirm with Glob, not from memory. |
| Do not | Suggest an implementation, read `node_modules`, or summarize file contents. |
| Return format | Grouped list: `package -> path:line — symbol — why relevant`. |
| Length cap | 25 lines. |
| Already known | The spec text, the workspace layout from CLAUDE.md, and the test command (`pnpm test`). |

### 2.2 Builder brief
| Field | Content |
|---|---|
| Goal | Implement `specs/<spec>.md` until every acceptance criterion (AC) is met and covered by at least one test. |
| Scope | The Scout map (passed inline), the spec, and the packages it lists. |
| May change | Source and test files inside the spec's packages. You may add new tests. Shared config and dependencies fall under L9. |
| Verify | Run `pnpm test` from the worktree root and include the pass/fail summary line, copied from the output, in your report. |
| Do not | Delete, skip (`.skip`, `xit`), or narrow (`.only`) any existing test. Don't edit `specs/`, CI config, `pnpm-workspace.yaml`, or packages the spec doesn't name. Don't spawn agents. Don't merge. |
| Return format | (1) AC to test-file mapping; (2) files changed, paths only; (3) **deviations from the spec, stated explicitly**, or "none"; (4) the test summary line, quoted. |
| Length cap | 40 lines. No diff bodies, no full logs. A log over 20 lines goes to a scratch file named in the report (see open questions). |
| Already known | The Scout map and the spec ID. For a rework, the Refuter's must-fixes, quoted exactly. |

### 2.3 Refuter brief
| Field | Content |
|---|---|
| Goal | Decide whether the Builder's worktree diff meets `specs/<spec>.md`. Treat the Builder's "done" as an unverified claim. |
| Scope | The spec, the diff (`git diff <base>...HEAD` in the Builder's worktree), and the Builder's deviation list only. You don't get the rest of the Builder's report. |
| May change | Nothing. |
| Verify | (a) Rerun `pnpm test` yourself. (b) Run `pnpm --filter "...[<base>]" test` on the affected packages. (c) Run every other check script that actually exists in root `package.json`, read from the file, not assumed. (d) For each AC, find the test that exercises it. (e) Grep the diff for removed tests, `.skip`, `.only`, `any` casts and `@ts-ignore`. |
| Do not | Edit files, suggest refactors outside the spec, or accept on "tests pass" alone if any AC has no test. |
| Return format | `VERDICT: ACCEPT` or `VERDICT: REWORK`; per AC: met / unmet + evidence (`path:line` or test name); must-fixes, numbered, each one actionable; any spec ambiguity found, flagged separately. |
| Length cap | 30 lines. |
| Already known | The spec ID and the round number. Don't re-check criteria an earlier round already marked "met" unless the diff touched them. |

### 2.4 Debugger brief (escalation only)
Same eight fields as the Builder brief, with these differences. **Goal:** find the root cause of the AC that failed twice. **Return:** 2 to 4 competing hypotheses, each with the observation that would confirm it and a proposed test (`CC_EG §5.8`). **Cap:** 35 lines. **May change:** instrumentation in its own worktree only. Its findings go back to the Builder as must-fixes. The Debugger never ships code.

## 3. Loop rules

**L1. Spec readiness gate.** Before spawning anything, the Orchestrator checks that `specs/<spec>.md` has numbered acceptance criteria and names the packages in scope. If either is missing, halt with H1. Don't fill in a missing criterion yourself `[generalizable]`.

**L2. Clean baseline.** Run `pnpm test` on the base commit first. If it's red before any change, halt with H2. Otherwise the Refuter can't separate the Builder's regressions from failures that were already there.

**L3. Sequence.** Scout, then Builder in a worktree, then Refuter, which is always a fresh spawn and never a fork. The Orchestrator reads only reports, never diffs or logs directly `[Anthropic docs — isolation: worktree; generalizable — orchestrator-as-reader anti-pattern]`.

**L4. REWORK routing.** Send the Refuter's must-fixes, quoted exactly, back to the **same** Builder by agent ID so it keeps its context `[Anthropic docs — resume by ID / SendMessage]`. Each round gets a **new** Refuter, so no reviewer judges its own earlier verdict.

**L5. Round cap.** Allow at most 3 Builder rounds per spec. If the same AC fails in round 2, run the Debugger once, then do round 3. Still REWORK after round 3: halt with H4. This matches the global 3-cycle rule.

**L6. Independence.** The Refuter never sees the Builder's reasoning, only the spec, the diff and the deviation list. Its Bash use is limited to `pnpm` and read-only `git`, enforced by a deny list (§4). Don't add a step where any agent "double-checks its own work". Re-checking without new evidence only adds cost (AEA §4.14).

**L7. Deviations are decisions.** If the Builder reports a deviation, the Orchestrator does not accept it on its own authority when the deviation changes behavior an AC describes. That halts with H3. Cosmetic deviations (naming, file placement inside the package) can be accepted and get a note in the change log.

**L8. ACCEPT means merge-gate, not merge.** After ACCEPT, the Orchestrator merges the worktree branch into a feature branch, never `main` (Tier 1 default). The gate runs `pnpm test` again on the merged result in CI or a hook; red blocks the merge. A prompt can't enforce that, so it lives in a mechanism `[generalizable — CC_EG §6]`.

**L9. Scope authorization.**
- **Autonomous:** source and tests inside the spec's packages; new test files; type and lint fixes in touched files.
- **Do it, then report:** changes touching 3 or more packages; adding a dependency (lockfile diff called out in the report).
- **Halt:** editing `specs/`, CI config, `pnpm-workspace.yaml`, root `tsconfig`, or published API contracts not named in the spec; deleting or skipping tests; `--force`; any git history rewrite; editing CLAUDE.md or settings files.

**L10. One spec in flight per Builder.** Parallel specs are allowed only when their package sets don't overlap, and never more than 2 Builders at once. Specs that share a package run one after another. That avoids merge conflicts between worktrees and keeps reports small.

**L11. Session stop.** Stop at the next loop boundary when any of these is true: all queued specs are accepted, a halt fires, or Orchestrator context reaches about 140K (70% of the budget in §5). End with the global closeout format.

### Halt-and-escalate triggers
| ID | Trigger |
|---|---|
| H1 | The spec has no acceptance criteria or no named packages, or two ACs contradict each other |
| H2 | The baseline `pnpm test` is red before any change |
| H3 | A Builder deviation changes behavior an AC describes |
| H4 | Still REWORK after round 3 |
| H5 | The Refuter finds a test deleted, skipped or narrowed, or a weakened type (`@ts-ignore`, `any` cast) |
| H6 | The Builder needs a change in the L9 halt list |
| H7 | A failure shows up in a package outside the spec scope (regression outside scope) |
| H8 | The Refuter flags spec ambiguity, so the verdict depends on how the spec is read |

A halt note gives what was attempted, what was observed, and which trigger fired. Use `output\halt_notes\` if the repo has it; otherwise report it in the session.

## 4. Cap mechanisms (enforcement, not prose)

`.claude/settings.json` excerpt. JSON has no comments, so the marker follows the block:

```json
{
  "env": {
    "CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "1",
    "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "3",
    "CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION": "40",
    "CLAUDE_CODE_DISABLE_WORKFLOWS": "1"
  },
  "permissions": {
    "deny": ["Agent(general-purpose)"]
  }
}
```
`[product fact 2026-09-09 — verify against the running Claude Code version]`

- **Spawn depth 1:** subagents can't spawn subagents. The Builder also has `Agent` removed from its tools.
- **Concurrency 3:** at most 2 Builders plus 1 Refuter at once (L10).
- **Workflows off:** ultracode stays off by default. Opt in per task only, for something like a repo-wide migration spec `[cc-delegation-patterns §6]`.
- **Refuter's Bash limit:** set in the Refuter's agent frontmatter with `disallowedTools` entries for write-capable git subcommands. Check the matcher syntax against current hooks and permissions docs `[speculation — exact Bash pattern syntax not verified this session]`.
- **Per-agent runaway:** handled by the `maxTurns` values in the role table.

## 5. Orchestrator token budget (assumed 200K window)

| Allocation | Tokens |
|---|---|
| System prompt, tools, agent descriptions | 25K |
| CLAUDE.md and rules | 8K |
| Spec text | 6K |
| Scout return (25-line cap) | 2K |
| Loop reports: 3 rounds × (Builder 1.5K + Refuter 1K) | 7.5K |
| Orchestrator reasoning and integration | 40K |
| Headroom (stop at 140K per L11) | 111.5K |
| **Total** | **200K** |

If the session runs on a 1M window, scale the headroom row only. The return caps stay fixed, because they are what keeps the Orchestrator's context from growing.

## 6. Handoff and round-trip

- **Handoff to Claude Code** happens when three files exist: the project CLAUDE.md (mission, authority matrix, L9), the agent files for `explore` / `builder` / `refuter` / `debugger`, and the settings block above. The first session runs the loop on one small spec as a pilot before you queue more.
- **Bring it back to a design session** when any of these happen: H4 fires on 2 or more specs (the specs are under-written, not the code); H5 fires at all; the same deviation class shows up in 2 or more sessions; or you want to add a role.

**Runtime governance:** `rootnode-critic-gate` would formalize the Refuter's verdict, but the loop already fills that gap. Leave it out unless the loop runs unattended overnight.

## Assumptions and open questions

- **Assumed:** the base branch is `main`; `pnpm test` runs across the whole workspace; and specs follow a common format. If the specs don't follow one, write a spec template first, because L1 depends on it.
- **Project code:** what's the Drayline prefix for this repo? It's needed to name the CLAUDE.md, the agent spec files and the scratch-log path (L9 / Builder brief).
- **Merge target:** can an ACCEPT merge into a feature branch on its own, or does every merge wait for you (L8)?
- **Dependencies:** are new dependencies acceptable with notification, or should they halt? I put them in "do it, then report."
