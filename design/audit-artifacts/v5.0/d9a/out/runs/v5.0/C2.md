# Deliverable: `prompts/{run_name}.md`

````markdown
# Autonomous run: three-phase DB migration (generate → apply to staging → update ORM models)

## Critical — read first
- UNATTENDED RUN. Nobody can answer questions. When a halt trigger fires, write the halt note
  and the session report, then stop. Do not guess past a halt.
- STAGING ONLY. No command in this run may touch any database except the one whose identity
  matches STAGING_EXPECTED_IDENTITY below. Never read, print or log the value of the DSN env var.
- Phase order is strict: Phase 2 starts only if every Phase 1 gate passes; Phase 3 starts only if
  every Phase 2 gate passes.
- Halt on END state, not starting state. Starting conditions are recorded only and are never a
  reason to halt. Halts are tied to the end-state checks in each phase.
- Never push. Never commit to BASE_BRANCH. Never use --force. Never rewrite git history.

## Parameters (operator fills before launch; pre-flight halts if any remain unfilled)
- RUN_NAME = FILL_ME
- BASE_BRANCH = FILL_ME
- MIGRATION_SPEC = FILL_ME            # path to the approved schema-change spec (the only source of intent)
- MIGRATIONS_DIR = FILL_ME
- MODELS_DIR = FILL_ME
- DSN_ENV_VAR = FILL_ME               # NAME of the env var holding the staging DSN, never the value
- STAGING_IDENTITY_CMD = FILL_ME      # prints "<host>/<database>" of the connected DB
- STAGING_EXPECTED_IDENTITY = FILL_ME
- STAGING_BACKUP_CMD = FILL_ME        # writes a restorable staging snapshot; prints its path
- MIGRATE_OFFLINE_CHECK_CMD = FILL_ME # renders/validates migrations without a DB connection
- MIGRATE_CURRENT_CMD = FILL_ME       # prints current applied revision id
- MIGRATE_UP_CMD = FILL_ME            # upgrade to head
- MIGRATE_DOWN_CMD = FILL_ME          # downgrade to a revision id passed as the last argument
- ORM_DRIFT_CHECK_CMD = FILL_ME       # exits 0 and prints no diff when models match the DB schema
- TEST_CMD = FILL_ME
- ROWCOUNT_CMD = FILL_ME              # prints "<table> <rowcount>" for each table named in MIGRATION_SPEC

## Mission
Turn MIGRATION_SPEC into reversible migration files, prove they apply and roll back cleanly on
staging, then update the ORM models so the drift check comes back empty and the test suite passes.
Success = three phases COMPLETED, every gate PASS with quoted evidence, and a session report in
reports/. A halted run that leaves an accurate report and staging at a known revision is an
acceptable outcome. A run that "finishes" without evidence is not.

## Scope
- In-scope: create files under MIGRATIONS_DIR; edit files under MODELS_DIR; run the parameter
  commands against staging; create branch `migration/RUN_NAME` from BASE_BRANCH; one commit per
  completed phase on that branch; write reports/RUN_NAME_status.md (append-only) and the session
  report reports/RUN_NAME_<YYYYMMDD-HHMM>Z.md (do not commit the report).
- In-scope with notification (do it, then record under Observations in the status file):
  touching any file outside MIGRATIONS_DIR and MODELS_DIR that the change requires, such as an
  import path or a test fixture. Changing more than 3 such files is a halt (trigger 9).
- Out-of-scope (halt): any edit to an existing migration file; CLAUDE.md, settings files, .git;
  deleting or skipping tests; installing or upgrading dependencies; any network target other than
  staging; push.

## Pre-flight (all before any file read beyond this prompt)
1. List the Skills available in this session. Record which are loaded and note any expected
   Skill that is missing (rootnode-critic-gate is optional here). Missing Skills are recorded, not a halt.
2. Parameter check: `grep -cE '^- [A-Z_]+ = FILL_ME$' <this prompt path>` must print 0. Otherwise halt (trigger 1).
3. Record for the report only. These never cause a halt:
   `date -u +%Y-%m-%dT%H:%MZ` · `git branch --show-current` · `git rev-parse HEAD` · `git status --porcelain | wc -l`
4. Staging identity: run STAGING_IDENTITY_CMD. Its output must equal STAGING_EXPECTED_IDENTITY
   exactly. Otherwise halt (trigger 2). Run this check again right before every command that
   writes to the database.
5. Record the pre-run revision: `MIGRATE_CURRENT_CMD` → PRE_REV. Record ROWCOUNT_CMD output → PRE_ROWS.
6. Run TEST_CMD on the untouched tree. If it fails, halt (trigger 3): the starting point is not clean.
7. `git switch -c migration/RUN_NAME BASE_BRANCH`

## Phase 1 — Generate migration files
1. Read MIGRATION_SPEC. Read the most recent existing migration in MIGRATIONS_DIR to match its
   conventions and to find the revision the new files must build on.
2. Write one migration per logical change in the spec. Every migration needs a working down step.
   A down step that is empty, or that only says "irreversible", is a halt (trigger 5).
3. Destructive operations (dropping a column or table, narrowing a type, NOT NULL without a
   default on a populated table) are allowed only if MIGRATION_SPEC names that exact operation.
   Otherwise halt (trigger 6).
4. Gates:
   - G1.1 `MIGRATE_OFFLINE_CHECK_CMD` exits 0.
   - G1.2 The new migrations form a single chain starting at PRE_REV, with one head. Show the
     revision ids from the files.
   - G1.3 Every operation in MIGRATION_SPEC maps to a migration. Write the mapping table into the
     status file, one row per spec item, citing file:line.
5. Commit on the run branch: `migration(RUN_NAME): phase 1 generate`. Append the Phase 1 result to the status file.

## Phase 2 — Apply to staging
1. Run STAGING_BACKUP_CMD and record the snapshot path. If it fails, halt (trigger 7). Never
   migrate without a snapshot.
2. Repeat the identity check (pre-flight step 4), then run MIGRATE_UP_CMD.
3. Round trip: run MIGRATE_DOWN_CMD with PRE_REV as the target, then MIGRATE_UP_CMD again.
   Repeat the identity check before each step.
4. Gates, all checked against the end state:
   - G2.1 `MIGRATE_CURRENT_CMD` prints exactly the head revision id recorded in G1.2.
   - G2.2 The round trip completed: the down step reached PRE_REV and the second up step reached head again. Quote both outputs.
   - G2.3 ROWCOUNT_CMD → POST_ROWS. Compare with PRE_ROWS. Any change not explained by the spec
     is a halt (trigger 8).
5. If any step in Phase 2 fails: run MIGRATE_DOWN_CMD with PRE_REV as the target exactly once.
   Record its result and the snapshot path, then halt (trigger 4). Do not retry the up step.
   Do not edit migrations to "fix forward".
6. Append the Phase 2 result to the status file. There is no commit, because Phase 2 changes no files.

## Phase 3 — Update ORM models
1. Edit MODELS_DIR so the models match the migrated staging schema. Change only what the
   migrations changed.
2. Gates:
   - G3.1 `ORM_DRIFT_CHECK_CMD` exits 0 and prints no diff.
   - G3.2 `TEST_CMD` passes. Quote the summary line.
3. A failure gets up to 3 fix-and-recheck cycles in total for that issue. On the 4th failure,
   halt (trigger 10).
4. Commit: `migration(RUN_NAME): phase 3 models`. Append the Phase 3 result to the status file.

## Halt-and-escalate triggers (any one → write a halt note to the status file, write the session report, stop)
1. A parameter is still FILL_ME.
2. Staging identity mismatch, or the identity command fails. Stop immediately, before any further database command.
3. Baseline TEST_CMD fails before any change.
4. Any Phase 2 database command fails (after the single rollback attempt in Phase 2, step 5).
5. A migration cannot be written with a working down step.
6. A destructive operation that MIGRATION_SPEC does not name exactly.
7. Staging backup fails.
8. Row counts change in a way the spec does not explain.
9. More than 3 files outside MIGRATIONS_DIR and MODELS_DIR need changes.
10. 3 fix cycles on one issue without the gate passing.
11. MIGRATION_SPEC is ambiguous: two reasonable readings that would produce different
    migrations. Record both readings and do not pick one.
12. A command or tool the prompt names is unavailable, or fails to start. Record the gate as
    NOT_RUN; it is never PASS.

## Verification rule
When you change code that can be run, built, or type-checked, run a real check that exercises the change before reporting it done: the project's tests, type-checker, or build, or the changed command itself. A syntax-only check, or a check command that failed to start, does not count; if all that is missing is the project's declared dependencies, install them with its own package manager and lockfile (e.g. npm install, pip install -r requirements.txt), never via sudo or the system package manager, unless told not to. Only if no real check can run here, say which one you did not run and why instead of reporting the change as done.
(Override for this run: dependency installation is out of scope. Treat a missing dependency as trigger 12.)
Banned at completion: "should work", "probably fine", "looks good". Every PASS quotes its evidence.

## Carry the work through
A standing instruction from the user, the person you are working for. It is about how your turns end. A message with no tool call in it ends your turn, and the work stops there until you are asked to continue. The user has seen you end turns in four ways while work they asked for was still owed, and does not want any of them. One: a long summary of what was done that closes by announcing the next step and has no tool call, so the next thing never starts. Two: an offer to carry on with something unless the user would prefer otherwise, which stops to wait for an answer the user was not going to give. Three: a list of decisions for the user when, by your own account, none of them blocks the rest of the work. Four: deciding that this is a good place to report, because the turn has been long or a milestone is done. Status notes are welcome, and so are your recommendations on open decisions, but put them in the same message as your next tool call and carry on with whatever does not depend on the user's answer. If you notice yourself inviting the user to redirect you or offering to wait, delete it and do the next thing. The stops the user does want are the ones where nothing can move without them, or where the thing blocking you is deliberately protected from you. This does not override the need for confirmation on risky or destructive actions.
(For this run, "stops the user does want" = the halt triggers above.)

## Final item — Write session report (on every outcome: COMPLETED, HALTED <trigger #>, BLOCKED)
Write to reports/RUN_NAME_<stamp>Z.md, where the stamp comes from `date -u +%Y%m%d-%H%M`. Do not commit it.
Fill every field by copying command output, not by recalling it:
- prompt: this file's path and `tr -d '\r' < <prompt path> | sha256sum`
- outcome, started, ended (`date -u`)
- pre_state: the pre-flight step 3 values, plus PRE_REV and PRE_ROWS (record only)
- post_state: `git rev-parse HEAD`; `MIGRATE_CURRENT_CMD` output; POST_ROWS; backup snapshot path;
  `tr -d '\r' < <file> | sha256sum` for each new migration file
- files_changed: `git diff --name-status BASE_BRANCH` plus `git ls-files --others --exclude-standard`.
  The count is the number of rows.
- gates: one row each for G1.1–G3.2, with id · command · PASS / FAIL / NOT_RUN · quoted evidence line
- findings: F-n · severity · path:line · open/resolved
- observations: each tagged [observed] or [inferred]
- not_verified: required. Write "None identified." only after checking. Always list this
  explicitly: staging data volume may differ from production, so lock duration and runtime on
  production are not verified by this run.
- staging_state_on_exit: the revision staging is left at, and whether it equals head or PRE_REV
Then stop.
````

## Launch requirements (outside the prompt)

- **Pump primer.** Before the first unattended run, run Phase 1 once interactively against this prompt. That catches parameter and convention mistakes while someone is still watching. `[generalizable: cc-prompt-design-patterns §6]`
- **Enforce the production guard with a hook.** The prompt only states the rule. A `PreToolUse` hook on `Bash` should block any command containing your production host or database name. A hook blocks only when it exits with code 2; any other non-zero exit is a non-blocking error and the command still runs `[Anthropic docs — hooks]`. Also add `git push` and `--force` to `permissions.deny` in the repo's `.claude/settings.local.json`. Make both changes yourself; the floor rules forbid me from editing settings files.
- **Hard time cap.** The agent can't enforce wall-clock time on itself. Set a Windows Task Scheduler job that runs `Stop-Process -Name claude -Force` at your cutoff. Every phase writes to the status file, so a run that gets killed is still auditable up to the last phase it finished.
- **Model.** Opus 5.5 at `medium` or `high`. The "Carry the work through" block is the verbatim Anthropic text for a fully unattended Opus 5.5 run `[Anthropic docs — Prompting Claude Opus 5.5]`. Change that block if you run a different model.
- **Single agent, no subagents.** The three phases depend on each other in order, and each gate checks something outside the agent's own output: the migration tool, the staging database, or the test suite. A separate reviewer agent would add cost without filling a gap here. `[generalizable: agent-warranted test]`

## Decisions for you before the first run

1. **Rolling back staging after a Phase 2 failure.** The prompt allows exactly one rollback to `PRE_REV`, then halts. The alternative is no rollback, which leaves staging partially migrated for you to inspect in the morning. I recommend keeping the one rollback; the snapshot taken in Phase 2 step 1 covers the case where the rollback itself fails.
2. **The up → down → up round trip runs the down steps against real staging data.** That's the only real test that rollback works, but on a populated table a down step can lose data. The snapshot covers this. Confirm that's acceptable for your staging environment.
3. **Commits on a local branch.** The prompt makes one commit per completed phase on `migration/RUN_NAME` and never pushes. If you'd rather review uncommitted changes in the morning, delete the two commit steps.
